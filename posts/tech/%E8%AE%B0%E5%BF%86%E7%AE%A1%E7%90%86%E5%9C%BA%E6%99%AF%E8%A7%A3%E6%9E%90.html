记忆管理场景解析

2026-09-28
14.5k
50m
技术

用户昨天在 App 里反馈商品破损，上传了照片，客服承诺今天给出处理结果。今天他换到网页，只问了一句：

昨天那件事怎么样了？

一个能搜索历史聊天的 Agent，也许能找到“商品破损”。但要把服务接下去，它还需要知道：是哪笔订单、照片是否已收到、昨天承诺了什么、谁负责处理、现在是否已退款，以及今天适用的处理规则。

这些信息分散在对话、工单、订单、支付和知识库里，更新速度也不同。记忆管理的价值，最终体现在 Agent 能不能带着正确的历史，把当前这件事继续做对。

本文先梳理 Agent 记忆的概念、设计路线与适用场景，再以客服为重点，讨论数据模型、读写链路、业务指标和迭代方向。

资料检索截至 2026 年 10 月 3 日，以原始论文、官方文档和项目仓库为主。文中的客服系统是综合这些机制提出的参考设计，案例与配置均为示意，不代表某家公司的线上实现或实测收益。配图为本文原创，文末提供 Excalidraw 可编辑源文件。

一、先说清楚：Agent 究竟在记什么 ​

在本文的讨论范围里，Agent 记忆是一个系统能力：从交互和执行中保留信息，让它能够影响后续决策，并在信息变化时被更新、纠正或删除。

这个定义包含三个动作：留下来、用得上、改得掉。 只把所有聊天存进数据库，完成的是记录；只有后续能选择性地读取并维护它们，才形成可用的记忆机制。

1.1 上下文、记忆、知识库与业务事实 ​

这几类东西都可能出现在 Prompt 里，但承担的职责不同。

对象回答的问题客服中的例子主要维护者
本轮上下文模型这一次实际看到了什么？当前问题、最近消息、本次查单结果上下文组装逻辑
会话／任务状态这件事进行到哪一步？已核验订单，等待补充破损照片工作流与状态存储
跨会话记忆以前发生过什么，哪些信息仍值得带过来？用户偏好文字沟通，上次方案已尝试且无效记忆服务与业务事件
业务知识这类问题应当怎样处理？某商品类型的退换货规则与生效版本业务规则与知识运营
业务事实源现在真实的业务状态是什么？支付系统记录退款成功订单、支付、CRM、工单系统

上下文是一次推理的输入集合，记忆是这个集合的一部分来源。RAG 则是一种检索后辅助生成的机制，可以检索知识，也可以检索记忆。

因此，RAG 与记忆存在交集，但不能画等号：只检索产品手册的机器人也能使用 RAG；把用户偏好保存在结构化字段中的 Agent，也不必通过向量检索才能使用记忆。

同样，长上下文扩大了本次能读取的信息量，没有自动解决跨会话保存、信息失效与访问权限的问题。Anthropic 的工程文章将压缩、结构化笔记与按需读取作为长任务的不同手段：压缩维持当前任务连续性，笔记保存以后还要用的信息，引用帮助 Agent 按需展开细节。参考：Effective context engineering

1.2 “短期”不等于放内存，“长期”不等于向量库 ​

LangGraph 的定义很有代表性：短期记忆属于一个会话线程的状态，可以通过 checkpoint 持久化；长期记忆跨线程使用，通过 namespace 组织。参考：Memory overview

这意味着，一个保存了三个月、可以恢复的工单线程，仍可能属于线程范围的记忆；一条刚写入、立即在另一个会话使用的沟通偏好，则已经是跨会话记忆。

时间长短、可见范围和存储介质，是三个不同的维度。 Redis、关系数据库、文件、向量索引和图数据库，都只是实现选择。

二、给记忆分类，要同时看几个维度 ​

“语义记忆”“长期记忆”“图记忆”“Agentic Memory”经常出现在同一份方案里，但它们并不处于同一层分类。

2025 年底的综述 Memory in the Age of AI Agents 提供了一个有用的研究框架：从表现形式、功能、动态过程三个角度看记忆。其中，表现形式包含 token、参数与隐式表示；功能包含事实、经验与工作记忆；动态过程关注形成、演化和检索。参考：综述原文

2.1 按功能：事实、经历、方法与工作状态 ​

认知架构 CoALA 区分工作记忆与不同长期记忆组件，为理解语言 Agent 提供了结构化视角。参考：CoALA

在业务里，可以用下面几个问题理解这些术语。不同论文的分类并不完全一致，以下是便于工程讨论的对应关系。

类型保存什么客服例子最容易混淆的地方
语义／事实记忆关于实体的陈述与知识用户明确表示希望通过站内信联系保存的是陈述，真实性还要看来源
情景记忆某次经历及其上下文某次设备故障中，重启无效，更换配件后恢复不能只剩“更换配件有效”，丢掉适用条件
程序性记忆可复用的做事方法某错误码的排查顺序从个案提炼的方法，需要验证后才能推广
工作记忆当前推理和执行所需状态目标、已尝试步骤、待办、当前证据不能把模型的推测直接作为已完成事项

这里的“语义记忆”描述内容类型，“语义搜索”描述检索方法。二者名字相近，但一条语义记忆完全可以通过 customer_id 精确查询。

2.2 按范围：属于谁、服务哪件事 ​

常见范围包括一次执行、一个会话、一个工单、一个用户、一个企业租户，以及经过整理的组织知识。

例如，“这单不要打电话，我正在开会”首先是本次工单的临时约束；“以后都请文字联系”才可能成为用户长期偏好。把前者永久写入用户画像，会把短暂情境误当成稳定习惯。

同一个用户也可能代表不同企业处理事务。用户身份相同，并不意味着不同企业的记忆可以混用。

2.3 按表达形式：文本、结构、参数与隐式状态 ​

应用层最容易控制的是显式外部记忆：消息、摘要、JSON、事件、笔记、关系图。它们可以查看、定位来源，也比较容易做局部更正。

更靠近模型的路线包括把知识或经验写进参数，以及用学习得到的隐式表示承载历史信息。这里的隐式记忆不能直接等同于普通推理服务中的 KV cache；具体机制取决于模型和研究方案。参考：记忆综述的形式分类

对于客服这样需要精确更新订单事实、解释来源和按用户删除数据的系统，我会优先选择显式外部记忆。稳定的通用服务能力可以进入训练流程，频繁变化的个人事实更适合留在可维护的数据层。这是基于可维护性的工程取舍。

2.4 按控制方式：谁决定记什么、何时读取 ​

控制者可以是固定规则、工作流、模型工具调用，也可以是专门训练的记忆策略。另一个独立选择是执行时机：在请求链路里同步完成，或在后台整理。

这些方式能够组合。例如：退款回执由业务事件确定性记录；聊天摘要由后台模型生成；用户说“记住我的偏好”时同步更新偏好；检索时由程序限定租户和工单，再允许模型决定是否展开历史。

Agentic Memory 主要描述记忆管理的自主程度，并不意味着必须使用某一种数据库。

三、现在有哪些主要设计路线 ​

下面按工程机制归纳。它们往往会同时出现在一个系统里，也没有从低级到高级的固定排序。

3.1 滑动窗口与上下文压缩 ​

最直接的办法是保留最近若干轮消息。进一步可以把更早的内容压缩成摘要，形成“摘要 + 最近消息 + 当前任务状态”的输入。

优点是实现直接，特别适合围绕同一主题推进的会话。代价是原文细节可能在压缩中丢失，而且摘要经过反复改写后可能越来越偏离源记录。

以退款对话为例，下面两种摘要看起来差不多，后续行为却会完全不同：

用户希望退款，客服已答应处理。

用户申请退款；客服承诺在明天 18:00 前反馈审核结果；尚未批准退款。

我会把目标、已确认事实、已执行动作、未完成事项和证据引用分别保留。摘要负责帮助接续对话，关键状态则进入明确字段。原始事件在规定保留期内仍可按引用展开。

适用条件： 问题主要是对话变长、近期状态容易遗失。若问题是跨月找回某个细节，仅做滚动摘要通常不够。

3.2 结构化画像与原子事实 ​

一种做法是维护用户画像，例如语言、沟通渠道偏好；另一种做法是把事实拆成多条独立记录。LangChain 的文档把这两种组织方式称为 profile 与 collection。参考：Memory overview

画像方便精确读取，独立事实便于分别更新和追踪来源。实际可以组合：画像作为当前有效信息的视图，底层事实保留各自的证据与版本。

例如，“喜欢简短回答”与“订单 O-1048 正在退货”不应共用一个生命周期。前者是偏好，后者是某个业务对象的阶段状态。

这一类设计的关键是明确字段的含义和更新条件。一次愤怒的表达不应该被永久提炼成“难沟通的客户”；模型猜测用户偏爱某品牌，也不应与用户明确选择的偏好具有相同地位。

适用条件： 属性相对明确、读取频繁，需要跨会话个性化或减少重复询问。

3.3 检索型记忆：事件切分、混合检索与重排 ​

把历史分成消息、事件或会话片段，建立索引，在新请求到来时找出相关内容。这条路线与 RAG 共享很多技术：关键词检索、向量检索、重排、时间过滤和上下文拼装。

Mem0 的代表性思路是从对话中提取值得保留的信息，结合已有记忆整合，再按需检索；论文还讨论了加入图表示的变体。参考：Mem0

工程上真正影响结果的，往往是下面三个选择：

  • 怎样切分。 把“提出退款—补充证据—拒绝原因”切散，单独召回一句“可以退款”就可能失去条件。
  • 怎样定位。 订单号、工单号适合精确匹配；“昨天坏掉的那台机器”才需要语义与时间线索。
  • 怎样展开。 命中一条事实后，必要时补充相邻事件、对应回复或原始附件，而不是固定塞入 Top-K 个孤立片段。

检索相似度只能表示相关程度。它不能决定记忆是否属于当前用户、是否有效、是否足以支持一个业务动作。

适用条件： 历史规模较大、问题表达多样，需要找回跨会话细节。

3.4 分层记忆与按需换入 ​

MemGPT 借鉴操作系统的分层存储思想，让有限上下文与外部存储配合，并通过控制流程管理信息进入上下文的时机。参考：MemGPT

在应用里，可以落成三层：少量稳定信息常驻；当前任务的状态保持活跃；完整历史和附件留在外部，通过引用按需读取。

例如，模型一开始只拿到工单摘要和事件 ID，用户追问“昨天你们原话是什么”时，再读取那条消息。这样既保留可追溯性，也避免每轮携带全部历史。

这里要付出的代价是额外的读取轮次。Agent 需要知道何时继续查，也需要一个完成任务所需证据已经足够的停止条件。

适用条件： 长任务、多文件、多附件，或必须在低上下文预算内保存可展开的细节。

3.5 图与时间记忆 ​

当问题涉及“谁、哪个对象、怎样关联、何时改变”，单个文本片段就不一定是最自然的表示。

Zep 论文提出基于时序知识图谱的记忆架构；Graphiti 项目强调持续接收数据、维护关系及时间信息，并结合多种检索方式。参考：Zep 论文、Graphiti 项目

客服里的典型关系是：某客户提出某工单，工单关联某订单，订单包含某设备，设备经历过两次维修。沿着关系可以区分“同一型号的问题”与“同一台设备的历史”。

时间也至少有两个视角：事实何时发生或生效，以及系统何时知道它。退款昨天成功、今天才同步回来，就是一个常见差别。

但图不会天然更准确。实体合并错误，反而会把别人的经历连接进来。如果关系只是“客户—订单—工单”，关系表和精确查询通常就能表达。应当在多跳查询和时序关系确实成为痛点时，再评估图的收益。

适用条件： 多实体关联复杂、关系变化频繁，需要解释历史状态或进行多跳查询。

3.6 自组织笔记与证据分层 ​

A-MEM 借鉴卡片笔记的组织方式，为新记忆生成描述、关键词等属性，与已有记忆建立联系，并允许新信息推动旧记忆表示的更新。参考：A-MEM

Hindsight 则明确区分世界事实、Agent 经历、实体摘要和持续演化的判断，并围绕 retain、recall、reflect 组织操作。参考：Hindsight

这两项工作提供了不同启发：前者关注信息之间怎样自动组织，后者关注不同性质的信息怎样分开表达。它们不是同一套架构。

我的理解是，这类方法适合知识不断增长、事先难以穷举分类的研究与工作助手。迁移到客服时，最值得保留的原则是：模型总结出来的判断，应当有明确的证据入口。自动建立的关联可以辅助排查，但不能直接变成用户标签或处理规则。

适用条件： 开放主题、多次探索、跨任务知识积累；需要为自动整合付出额外计算和质量管理成本。

3.7 从经历中学习做事方法 ​

Generative Agents 将经历的保存、检索、反思与规划结合；Reflexion 则利用任务反馈生成语言形式的反思，帮助后续尝试改进。参考：Generative Agents、Reflexion

在工程实践中，一个值得复用的经历至少应该留下：任务条件、采取的动作、观察到的结果，以及方法的适用边界。单独保存“下次注意检查参数”几乎没有可执行价值。

对客服来说，“这个型号在某固件版本下，某错误码优先检查网络配置”可能值得成为候选经验。但一个案例成功，不足以说明因果关系；最终进入排查手册，还需要多案例验证和业务审核。

适用条件： 问题重复出现、过程有明确反馈，能够把个体经验整理成稳定方法。

3.8 学习记忆管理策略，以及长期压缩 ​

2026 年的 AgeMem 将长期与短期记忆操作作为 Agent 的工具动作，并通过强化学习训练存储、读取、更新、摘要和丢弃等决策。参考：AgeMem

2026 年 9 月的 MemForest 则关注长期积累后的存储与检索成本：按事件组织历史，通过树结构渐进合并冗余记忆，并结合时间邻域检索。参考：MemForest

前者探索“怎样学会管理记忆”，后者研究“已有记忆怎样更经济地组织”。证据成熟度也有区别：AgeMem 的论文页面已标注 ACL 2026；本文对 MemForest 的介绍则依据其 2026 年 9 月的预印本。论文中的压缩比例、准确率或延迟变化，仍需结合复现和自己的业务数据判断，不能直接当成客服上线后的收益。

这两条路线也给出一个实际提醒：记忆系统运行半年以后，问题会从“能不能记住”扩展到“哪些值得持续占用资源”。

3.9 框架与托管服务，提供的是实现工具 ​

LangGraph 提供线程状态持久化与跨线程存储；Amazon Bedrock AgentCore Memory 的官方文档列出用户偏好、语义信息、会话摘要和情景记忆等内置策略。参考：LangGraph 记忆、AgentCore 内置策略

这些能力可以缩短实现路径，但不能代替业务定义：哪句话值得保留、哪类信息有权跨会话使用、谁能纠正、何时失效，仍需要由产品和工程团队确定。

我会按下面的顺序选型：先列出任务需要的信息与更新规则，再确定存储和检索方式，最后选择适合接入现有系统的框架或服务。

四、记忆管理是一条完整生命周期 ​

前面的路线主要解释记忆怎样表示和使用。一条记忆真正进入系统后，还要经历筛选、维护和退出。

图 2：记忆不是一次写入后的静态记录。来源、适用范围和有效状态需要跟着它一起流转。

4.1 写入：区分值得记住与仅仅出现过 ​

可以按四个问题筛选：未来是否可能复用，来源是否清楚，能否确定作用范围，是否允许为这个目的保留。

一次物流查询产生的大段工具输出，可能只需要保留查询时间、状态与结果引用；用户明确要求“这个工单只通过文字联系”，则应进入当前工单的约束。

模型提取的结果先是候选。对于订单状态这类已有结构化来源的内容，应直接消费业务事件，避免绕一圈让模型从自然语言中猜出事实。

4.2 整合：重复、补充、变化和矛盾要分开 ​

“仍希望文字联系”可能是重复确认；“工作日文字，周末可以电话”是补充条件；“以后可以电话联系”是偏好变化；“我从未同意过电话联系”则涉及纠正历史。

这些情况不能统一成“把相似文本覆盖掉”。尤其当旧状态仍有解释价值时，需要保留它在什么时间范围内成立，以及被哪个事件替代。

4.3 读取：先确定范围，再判断相关性 ​

一个可落地的读取顺序是：确定身份和任务对象，限定允许访问的记录，排除对当前用途已失效的信息，再进行召回、重排和上下文组装。

对于“当时为什么拒绝退款”这样的历史问题，旧规则可能正是必要证据；对于“现在还能不能退款”，则需要查询当前适用的规则。失效不是简单的“永远不再读取”，而是它不再能被当作当前事实。

4.4 使用：把证据与结论一起交给模型 ​

只给出“用户已获赔”，模型很难判断还能不能继续赔付。更有用的表达包括：哪个订单、补偿类型、状态、发生时间和来源。

信息进入上下文时，也应标明角色：用户陈述、系统事实、人工判断或模型推断。历史消息里出现的指令，仍然只是历史内容；它不会因为被记忆系统存储，就获得改变权限和规则的能力。

4.5 遗忘：到期、纠正、失效和删除各有语义 ​

遗忘不应只有一个 delete 动作。临时约束可以到期；被新信息替代的事实可以退出当前视图；用户要求删除的数据，需要处理相应的源记录和派生副本；个案经验可以在流程变化后停止推荐。

设计时要同时检查摘要、向量索引、缓存和聚合画像。只删除原始消息，但留下能还原同一信息的摘要，并没有完成预期的数据移除。

业务审计记录与个性化记忆可以采用不同的保留和访问安排，但保留期限应由具体业务及数据治理要求确定，不能由模型临时决定。

五、记忆管理确实需要分场景 ​

决定设计差异的，通常是任务跨度、事实变化速度、错误代价和协作范围。

场景最值得记的内容可以优先尝试的组合主要评价问题
单次知识问答当前问题和已消歧的信息会话状态 + 知识检索回答是否准确，有没有必要保存个人信息？
个人助手稳定偏好、计划、长期约束用户画像 + 事件检索 + 时间管理是否减少重复说明，是否误用旧偏好？
编程 Agent目标、决策、失败尝试、任务进度文件笔记 + checkpoint + 代码按需读取能否在恢复后继续正确修改？
研究 Agent来源、论点、证据关系、未决问题检索 + 自组织笔记 + 引用关系结论能否回溯，矛盾证据是否保留？
教育辅导已掌握概念、误区、练习表现学习状态 + 情景记录 + 定期复核是否根据真实表现调整教学？
多 Agent 协作公共任务状态、明确结论、交接事项私有工作区 + 共享状态 + 版本化交接是否发生重复劳动和相互覆盖？
客服问题连续性、处理状态、历史承诺、解决结果工单状态 + 事件账本 + 实时业务查询 + 有限用户偏好是否真正解决问题，并减少再次来访？

这里的选择是本文的工程建议，不是对所有产品的统一架构要求。

有些应用最好的选择就是少记。如果用户只问“你们几点营业”，完整的用户长期记忆可能没有边际价值。另一些应用的关键则是任务记忆：编程助手要接着修复问题，不一定需要先记住用户最喜欢哪种表达风格。

设计应当从下一次决策需要什么开始，而不是从能收集多少历史开始。

六、客服的核心诉求：把一件事持续处理到结束 ​

客服当然需要个性化，但我会优先保证问题连续性和处理正确性。

用户未必在意 Agent 是否记住自己的表达风格，却往往在意下面这些事：为什么又让我提供一次订单号，为什么又让我重启一次，为什么昨天答应的事今天查不到，以及退款到底有没有执行。

所以，在客服里，我会把建设顺序设为：接续问题 → 保持业务状态正确 → 追踪承诺 → 复用解决经验 → 改善个性化体验。 具体顺序可以随业务变化，但应当能用服务结果解释。

6.1 不同客服业务，需要不同重点 ​

客服类型记忆重点典型动作容易产生的错误
售前咨询本次购买意图、预算、已澄清条件延续商品比较，减少重复介绍把一次预算永久当成消费能力
交易售后订单、凭证、退款／换货进度、已作承诺恢复处理流程，查询最新结果把“已申请”说成“已完成”
技术支持环境版本、错误码、尝试步骤和结果接着排查，避免重复无效操作在版本变化后照搬旧方案
企业客户服务组织、角色、服务范围、跨部门工单在授权范围内协调处理将联系人个人记忆混入其他企业
投诉升级争议点、证据、承诺、负责人、处理时间线给人工完整交接，追踪后续用一句负面标签替代客观经历

这也解释了为什么不能只做一个通用的 user_memory 集合：很多重要信息属于某笔交易或某个问题，而非用户的永久属性。

6.2 工单、会话和问题，并不总是一一对应 ​

一次会话可能讨论两笔订单，一个问题可能跨三次会话，工单还可能被拆分或合并。

因此需要区分：渠道会话标识、稳定的业务问题标识，以及订单、设备、合同等业务对象。工单号可以作为问题标识，也可以另建关联层，但不要默认“新会话 = 新问题”。

否则，用户换渠道后容易失忆；在同一会话里切换订单时，又容易把上一单的补偿和当前订单混在一起。

七、一套客服记忆架构应该保存哪些东西 ​

我更倾向于把存储职责拆清楚，再通过一个读取入口组装上下文。这个入口负责知道“去哪取什么”，不必把所有东西复制到同一个库。

图 3：记忆帮助 Agent 延续历史；订单、支付、权限和规则系统继续提供各自负责的事实与约束。图中表达逻辑数据流，关键状态应完成可靠记录后，再向用户确认。

7.1 六类信息，各自有明确归属 ​

信息推荐表示更新依据使用方式
当前工单状态结构化字段 + 短摘要工作流转换、工具回执、人工操作每轮按工单精确读取
原始交互与业务事件带来源的事件记录对话消息与业务事件审计、回放、必要时展开
用户沟通偏好带范围和来源的事实记录用户明确表达或确认只取当前相关且有效的偏好
工单中的承诺可追踪的待办对象承诺建立、变更、履行事件按状态与截止时间读取
历史处理经历条件—动作—结果—证据工单过程与确认的结果同类问题检索
组织处理方法版本化知识与流程业务审核发布按适用条件、规则版本使用

交易的实时状态从业务系统查询。记忆中可以保存“在某时刻查到的状态快照”，但要保留查询时间，并清楚它只是当时的观察。

7.2 用 namespace 组织，用权限系统授权 ​

可以采用类似下面的逻辑层级：

text
tenant / customer / preferences
tenant / case / state
tenant / case / events
tenant / case / commitments
tenant / product / reviewed_playbooks

这些路径描述组织方式，不天然构成安全边界。真正的访问范围应由当前登录身份、租户关系、工单归属和岗位权限计算，查询和写入都要使用这个范围。

对于跨 App、网页和电话的续接，需要经过业务允许的身份关联。姓名相同、文本相似或电话尾号相同，都不应成为自动合并客户记忆的充分依据。

共享设备、代下单和企业联系人尤其容易造成误归属。暂时无法确定关联时，可以要求用户补充订单信息；此时少读一点历史，比把别人的经历接进来更合理。

7.3 一条记忆要能回答“为什么相信它” ​

不是每条记忆都要设计几十个字段，但至少应覆盖内容、归属、来源、时间和状态。下面是一个仅作用于当前工单的沟通约束示意：

yaml
id: mem_284
scope:
  tenant_id: shop_a
  customer_id: customer_17
  case_id: case_92
kind: communication_constraint
content: 本工单通过站内信联系
epistemic_status: user_stated
source_refs: [message_731]
recorded_at: 2026-10-01T10:00:00+08:00
valid_from: 2026-10-01T10:00:00+08:00
expires_on: case_closed
status: active
version: 1

user_stated 表示这是用户表达过的要求。它不是对外部事实的核验结果。如果记录的是“包裹已经退回”，来源仍是用户消息时，就不能直接写成仓库已收货。

对于模型推断，应使用不同标记，并保留支持它的证据。模型输出一个很高的置信度，并不等于这条信息具有可校准的真实性概率，更不等于它有资格触发退款。

7.4 承诺需要单独建模 ​

“明天给您回复”如果只藏在聊天摘要里，后续系统很难判断是否超时、谁负责、是否履行。

我会把承诺表示为一个业务对象：

yaml
id: commitment_33
case_id: case_92
action: 反馈破损售后的审核结果
owner_queue: aftersales_review
due_at: 2026-10-02T18:00:00+08:00
status: open
created_from: message_742
fulfillment_refs: []

状态可以是待履行、已履行、已取消或已调整，具体由业务定义。截止时间、责任队列和履行证据使它能进入运营系统。

这里保存的是“承诺反馈审核结果”，没有隐含“承诺退款”。即使客服过去作出了越权承诺，也应保留发生过的事实并进入升级处理，而不是让记忆赋予系统额外的执行权限。

记住承诺与执行承诺，是两项能力。 到期检查由调度或工单系统触发，是否允许主动联系、使用哪个渠道，由已有的业务授权控制。记忆服务本身不会因为保存了日期，就自动具备可靠的提醒和履约能力。

7.5 事件、状态和摘要之间的关系 ​

事件记录“发生了什么”；状态回答“目前进行到哪里”；摘要帮助人和模型快速理解。

这三者可以相互关联，但用途不能互相替代。

图 4：退款申请、审核通过与退款成功是不同事件。当前状态由明确事件推进，摘要带着来源解释它。

对高价值状态，优先根据业务事件或权威查询结果更新。摘要生成失败，不应导致退款状态退回；摘要写出了“已退款”，也不应成为状态前进的依据。

事件记录可以采用追加与更正的方式保留过程。这里强调的是可追溯的逻辑，并不意味着所有个人数据都必须永久保存。

八、落地时，怎样读、怎样写、怎样处理变化 ​

8.1 读取链路：从问题定位到上下文组装 ​

用户问“昨天那件事怎么样了”，可以按下面的顺序处理。

第一步，确定当前身份与可访问范围。 从已认证渠道获取租户和客户信息，不把模型猜测的身份当成查询条件。

第二步，定位本次问题。 优先看当前会话绑定的工单与用户明确提供的订单信息。若存在多个候选问题，先消歧，再读取详细历史。

第三步，按业务键读取必要状态。 工单阶段、已完成步骤、待办和未履行承诺，直接按对象标识查询。它们不需要与大量历史片段竞争向量检索名次。

第四步，刷新会改变决策的事实。 退款状态、发货进度、服务资格等，根据本次意图查询相应业务系统。没有相关需求时，不必每轮查询所有后端。

第五步，检索补充经历。 例如查找上次排障失败的步骤，或用户提到的某张凭证。召回结果带来源、时间和对象范围，必要时展开上下文。

第六步，组装本轮输入。 把任务目标、确定状态、用户陈述、未决问题、规则依据和证据引用分别表达，让模型知道哪些内容支持哪些结论。

可以把输入理解成一个任务包：

text
当前请求：查询 case_92 的处理进度
当前业务事实：退款已提交，支付系统仍在处理中；查询于本轮
历史处理：照片已收，审核已通过；附对应事件引用
未完成事项：尚无退款成功回执
对客承诺：今天 18:00 前反馈审核结果
沟通约束：本工单使用站内信
适用规则：订单对应的售后规则及版本

上下文预算应向当前目标和关键证据倾斜。长期偏好只有在影响当前交流时才进入；大量相似旧工单可以只带一个合适案例或几个引用。

排序也不必急着设计一个复杂公式。先做范围、权限和有效性筛选，再结合对象匹配、时间相关性、来源可信程度与内容相关性排序，通常更容易解释和调优。

8.2 写入链路：立即可用的信息与后台整理分开 ​

LangChain 官方文档把记忆更新区分为请求链路上的更新与后台更新，并指出前者影响响应时延，后者会带来可见性延迟。参考：Writing memories

在客服系统中，我会根据业务需要进一步划分：

更新内容时机建议理由
工单绑定、关键步骤与已确认承诺对外确认前完成相应的可靠记录下一轮需要立即接续
退款、发货、核验等执行结果根据业务回执或后续权威查询记录不能由回复文本推导成功
用户明确要求纠正或忘记的信息先让在线读取立即遵守新状态避免随后继续误用
会话摘要与历史主题整理后台处理可容忍一定生成延迟
经验提炼、相似案例合并结案后或批量处理需要完整过程及结果证据

这里需要保证的是关键状态可靠可见，并不是每轮都同步调用一次模型“生成长期记忆”。

业务事务与事件投递可以采用事务内事件记录、可靠消息等现有机制。消费者按事件标识处理重复投递，并通过业务版本或因果顺序防止旧事件覆盖新状态。不能只依据“哪个消息最后到达”来判断哪个状态更新。

如果摘要处理有延迟，读取链路可以携带“上次摘要 + 摘要之后的新事件”。这样新一轮不会因为后台尚未完成，就忘记刚刚确认的事情。

8.3 一致性分级：哪些可以等，哪些不能等 ​

沟通风格晚一点更新，通常只是体验差异；漏掉刚提交的退款操作，就可能造成重复执行。

我会明确三类一致性要求：

  • 当前任务的连续性： 对已经确认接收的关键事项，后续读取应能看到相应记录；跨渠道续接也要有明确的可见性约定。
  • 外部业务执行： 以业务系统的请求标识、回执和状态查询为准；超时不能自动解释为失败，也不能直接宣称成功。
  • 摘要与经验： 可以延迟生成，但要标明整理到哪个事件或版本，避免被误认为覆盖了全部最新历史。

并发修改同一工单时，需要遵循它的版本或事件序列。一位人工客服补充的最新结果，不应被另一条基于旧快照生成的摘要覆盖掉。

这些机制可以复用现有后端能力。没有必要为记忆系统另造一套交易一致性语义。

8.4 冲突处理：按字段确定权威来源 ​

“永远信任最新信息”不够准确。最新的用户描述、晚到的旧事件，以及实时查询结果，可能表达的是不同事情。

冲突如何保留与判断
用户说已寄回，仓库尚未入库分别记录“用户报告寄出”与“仓库未确认收到”，继续查物流
昨天客服承诺退款，今天系统显示未提交保留承诺，核查执行缺口；不把承诺改写成执行成功
旧偏好是电话，用户明确改为文字在对应范围内更新有效偏好，记录此次变更来源
旧工单采用的规则与当前规则不同根据订单、地区、时间和过渡安排确定适用版本
旧接口结果晚于新结果到达按业务版本或事实时间处理，避免回退状态

权威来源应由字段和业务职责决定：支付系统负责退款执行结果，用户本人负责表达当前沟通偏好，规则系统负责适用政策，人工处理记录负责记载其实际判断。

有争议时，应把差异展示出来并继续核查，而不是让模型把两段冲突文本“融合”成一句看似流畅的结论。

8.5 纠正与删除，要影响整条派生链 ​

如果用户纠正“那张订单不是我的”，需要改的不只是摘要中的一个名字，还包括错误的工单关联、画像事实、索引和可能据此生成的后续结论。

一种实用做法是让派生记录保留来源引用。源记录被纠正或禁止使用后，在线读取先排除它及受影响的派生内容，再重建摘要和索引。删除或更正期间的异步任务，也要遵守新的记录状态，避免把旧内容重新写回来。

对用户而言，产品里最好能够解释“记住了什么、为什么记住、作用在哪、怎样修改”。这同时为人工客服提供了修正入口：记忆不是只能由后台开发人员操作的黑盒。

九、用一个跨渠道售后案例串起来 ​

下面是一个虚构案例。客户在 10 月 1 日反馈订单 O-1048 中的商品破损，问题归入工单 case_92。

图 5：同一工单跨越多个会话，记忆保留问题连续性，新的业务回执不断改变当前状态。

9.1 第一天：记住已经发生的事和真正作出的承诺 ​

用户在 App 上传照片，并说“这个事文字联系我就行”。客服确认收到材料，承诺第二天 18:00 前反馈审核结果。

此时应留下四类记录：工单与订单的关联、照片已接收的事实及引用、本工单的沟通约束，以及有责任队列和截止时间的承诺。

不能提前记成“退款已批准”，也不应将一次工单约束提升为永远不接电话的长期偏好。

9.2 第二天：用户换渠道，只问进度 ​

网页渠道完成身份确认后，系统关联到同一客户及工单。Agent 读取到已经收过照片，因此不需要再次索要；读取到待履行承诺，因此知道这次查询的服务背景。

随后查询审核系统。若状态仍为待审核，可以回答：

您昨天提交的破损照片已收到，这笔售后目前仍在审核。工单记录的是今天 18:00 前反馈审核结果。

如果系统还需要进一步查询或升级处理，就说明已实际执行的动作。只有升级操作成功，才说“已升级”；不能为了安抚用户生成一个不存在的处理进度。

这个环节的价值很具体：用户少解释一次，客服少找一次历史，系统也没有越过事实作出新承诺。

9.3 审核通过以后：提交、处理与成功分开 ​

审核通过只意味着具备下一步条件。是否可以提交退款，还要满足业务流程中要求的确认和权限。

提交成功后，业务系统返回退款请求标识。此时可以记录“退款已提交，处理中”。只有收到成功回执，或权威查询确认成功，才能更新为“退款成功”。

如果提交请求超时，就沿着同一个业务请求标识查询结果。历史里存在“尝试提交”的记录，能帮助 Agent 发现需要核查，但防止重复退款仍应依靠业务接口的幂等机制。

9.4 结果到达：履行承诺、确认解决，再整理经验 ​

审核结果送达用户后，可以将“反馈审核结果”的承诺标记为已履行。退款是否到账、用户的问题是否彻底解决，则按各自的业务定义继续跟踪。

工单关闭后，临时沟通约束退出活跃状态；处理经历保留条件、动作、结果和引用。若许多案例共同暴露出某型号包装的问题，可以进入质量分析流程。

从个案进入组织知识之前，需要去掉无关个人信息、核查共同条件，并由业务负责人确认。某个用户这一次得到的特殊补偿，不能自动变成所有用户都适用的新政策。

十、怎样与客服业务结合，并证明记忆有用 ​

10.1 先选一个可以闭环的目标 ​

“做一个长期记忆平台”太大，也很难判断第一版是否成功。我会先选一种明确的失败：例如，已上传过凭证的用户，在跨渠道续接时仍被要求重复上传。

这件事可以被拆成可观察环节：凭证接收事件是否记录，是否关联正确工单，新渠道是否定位成功，读取是否返回该事实，Agent 是否在回复中正确使用。

第一版由此可以很小：可靠的工单关联、结构化材料状态、来源引用和一个读取入口，就可能覆盖主要问题。是否需要语义检索，要看剩余失败是否来自无法定位历史。

10.2 把责任接到现有业务岗位 ​

参与方应当负责的定义或动作
客服运营什么叫问题解决、承诺履行、重复追问与有效转人工
业务系统团队状态来源、执行接口、事件语义与版本
Agent 团队信息提取、任务定位、检索和上下文使用
知识运营／产品负责人经验审核、规则适用范围、发布与失效
质检与数据团队失败样本、指标口径、灰度对照与误用分析

人工接管时，交接内容也应来自同一套状态：客户目标、已确认事实、已尝试动作、未完成事项、承诺和证据入口。只生成一段“用户情绪较激动，请尽快处理”，对下一位客服几乎没有帮助。

10.3 评估分三层：记对、用对、做对 ​

LongMemEval 检验信息提取、跨会话推理、时间推理、知识更新和证据不足时不作答等能力；LoCoMo 关注长跨度对话中的记忆表现。它们适合帮助设计记忆能力评估。参考：LongMemEval、LoCoMo

客服还要检查实际动作。τ-bench 通过模拟用户交互、业务工具与规则，比较最终数据库状态和目标状态。它并不是专门的长期记忆基准，但提示我们：对客回复听起来正确，不代表业务已经做对。参考：τ-bench

据此，可以把评估拆成三层。

层次关键问题适合观察的指标
记对归属、内容、来源、范围和时间是否正确？错误事实写入率、关键事项遗漏率、更新延迟、纠正传播完成度
用对是否检索到了该用的证据，排除了不该用的内容？关键证据召回、来源可追溯率、过期信息误用、跨对象串用
做对是否推进了正确的业务结果？任务成功、重复追问、承诺履行、同问题再次来访、处理成本

应把写入和读取分别观察。某条关键事实从未正确入库，单纯更换 embedding 模型通常无法补救；事实已经召回，模型却混淆“申请”和“完成”，问题则在使用环节。

10.4 业务指标需要明确分母和观察窗口 ​

只看“转人工率降低”容易误判。如果机器人阻止用户转人工，数字可能很好看，服务结果却更差。

几个更适合客服记忆的口径如下，窗口长度按业务节奏确定：

  • 重复索要率： 在已持有且仍有效、允许复用的信息场景中，再次无必要索要同一信息的工单占比。必要的身份核验与信息刷新单独统计。
  • 承诺按时履行率： 观察期内到期的有效承诺中，有证据表明按时履行的比例。改期和取消应单独展示，避免通过改期美化结果。
  • 同问题再次来访率： 在统一观察窗口内，已宣告解决的同一问题再次发起来访的比例。要解决跨渠道与工单拆分后的问题归并。
  • 有效解决成本： 将模型、检索、存储、记忆整理、人工接管及返工成本，除以经既定标准确认解决的问题数量。

同时保留满意度、人工质检和未解决投诉作为对照。AHT，即平均处理时长，可能在首次认真核查时上升，但整体再次来访下降；应结合完整服务链路判断。

上线前，建议建立包含真实失败类型的脱敏回放集：临时偏好与长期偏好、用户纠正、晚到事件、多订单混淆、重复工具请求、政策变更、删除后的再次查询，以及转人工后恢复。

回放必须按时间推进。评估“第二天上午该怎么回答”时，只允许读取当时已经存在的信息，不能偷看下午的退款回执或最终结案摘要。

10.5 用对照找出收益来自哪里 ​

一个实用的对照顺序是：无跨会话记忆；仅提供工单结构化状态；增加摘要与历史检索；最后再增加用户偏好或经验检索。

这些对照回答的是不同问题：是不是光把工单接好就够了，语义检索有没有进一步收益，个性化是否值得增加写入和治理成本。

对比时要保持模型、工具权限、知识规则和样本范围尽量一致。灰度分组也要避免同一客户或同一工单在不同渠道反复切换实验组，污染结果。

若效果变差，先定位在哪一步：提取错了、归属错了、记录过期、检索漏了、上下文被挤掉，还是模型看到了却用错了。失败原因决定下一次改动，而不是默认升级成更复杂的记忆架构。

十一、从第一版到持续迭代 ​

图 6：迭代以问题和证据推进。新增能力必须解释它改善了哪个环节，以及引入了什么成本。

11.1 第一阶段：先让同一件事接得起来 ​

打通身份、问题对象和跨渠道工单关联，保存关键状态、材料引用、承诺和交接信息，接入实时业务查询。

这一阶段不必先部署图数据库，也不必为每位客户提取完整画像。重点看重复解释和状态误报能否减少。

11.2 第二阶段：让历史细节找得到、变化跟得上 ​

当失败样本表明摘要和结构化状态不足以回答问题时，再加入事件检索、时间过滤、按需展开与有限的用户偏好。

同步补上可纠正、可删除、可追踪来源的机制，并观测异步处理延迟。如果检索收益有限，而写入成本明显增加，就收缩记忆范围或调整粒度。

11.3 第三阶段：让经过验证的经验可以复用 ​

从结案记录中提取候选方法，保留适用条件、成功与失败证据，经业务审核后进入版本化知识或流程。通过小范围发布观察结果，再决定推广。

需要允许撤回。当产品版本、接口或政策改变时，关联的旧经验应被重新验证或停止推荐。长期记忆的价值依赖持续维护。

11.4 后续值得关注的方向 ​

第一，按任务收益学习记忆策略。 AgeMem 等研究提示，记忆读写本身可以成为学习对象。客服里的目标不能只有少用 token，还应包含正确解决、少重复执行以及承诺履行。奖励定义不清晰时，自动学习可能优化到错误目标。参考：AgeMem

第二，从记住对话走向记住工作环境。 2026 年的 LongMemEval-V2 把关注点扩展到环境状态、工作流、常见陷阱和问题前提等经验，截至检索时原文标注为进行中的研究。它启发我们评估客服 Agent 是否学会了工具和流程的实际使用条件，而不只是记住用户说过什么。参考：LongMemEval-V2

第三，多模态证据的联合管理。 客服已经面对照片、录音和截图。后续设计需要保留原始证据、提取结果、版本和来源之间的关系；一张照片的描述可以帮助检索，但不应完全替代照片本身在争议核查中的作用。

第四，从单个 Agent 记忆走向团队连续性。 用户在机器人、人工客服和专业处理队列之间流转，真正需要连续的是同一个业务问题。共享层可以保存确认状态与待办，局部推断留在各自工作区，明确谁有权推进业务状态。

第五，把长期压缩做成可解释的维护。 像 MemForest 这样的研究关注冗余合并，但在客服里，还需要解释为什么一段记录可以降级、合并或删除。未履行的承诺不会因为很久没被访问就失去价值；已经过期的促销规则，也不会因为经常被检索就重新有效。参考：MemForest

对我来说，客服记忆管理最值得追求的结果是：用户再次联系时，Agent 清楚这件事已经走到了哪里，哪些信息仍然可靠，接下来该由谁完成什么动作。

实现这个结果，需要把模型的理解能力接到明确的业务对象、事实来源和反馈过程上。记忆保存下来的，才会逐渐成为服务能力。
