一个 Coding Agent 修复了一处错误。它读代码、调用工具、看到报错、调整方案，最后交出了能工作的修改。这已经是一种很有价值的能力，但下一次遇到相似问题时，它可能还会经历同样的弯路。

如果它进一步发现，弯路来自自己读取文件的方式、组织上下文的策略或选择工具的流程，并把改进保存成下一版 Agent；如果下一版还能够继续改进后续版本，问题就开始触及 RSI：**Recursive Self-Improvement，递归自我改进。**

2025 年的 Darwin Gödel Machine，以及 2026 年关于 AI 研发自动化的讨论，让这个老问题重新热了起来。但“失败后重试”“保留一条反思”“修改自己的代码”“自主研发下一代模型”，经常被放进同一个故事。它们改变的对象、需要的证据和距离目标的远近，都不一样。

我想沿着三个问题展开：**改了什么？由谁验证？下一轮是否继承改动？** 再追问更关键的一步：继承改动的新系统，是否也更擅长推动下一轮改进？

## 一、ReAct 与 RSI 不在同一层

ReAct 是一种组织 Agent 推理与行动的方法。RSI 是关于系统如何改进自身，以及这种改进如何继续推动后续改进的研究问题。两者可以出现在同一个系统中。

### 1.1 “自己”究竟指什么

在大模型语境里，我们容易把“AI”理解成模型权重。但实际运行的 Agent 还涉及提示词、上下文组织、工具、记忆与控制流程。模型保持不变，修改其他部分，也可能明显改变整个系统的能力。

为了方便讨论，可以把第 $k$ 版 Agent 写成：

$$
A_k = (\theta_k, P_k, M_k, T_k, C_k)
$$

其中，$\theta$ 是模型参数，$P$ 是提示词，$M$ 是持久记忆，$T$ 是工具实现，$C$ 是控制流程。这是本文的工程抽象，各部分在实际系统中可能交织。

看到“AI 改进了自己”的说法，我会先问：哪一个部分发生了变化，变化保存在哪里，后续运行是否真的使用了它？

| 发生的变化 | 一个例子 | 能说明什么 |
| --- | --- | --- |
| 本次输出变化 | 根据反馈重写一段答案 | 这次回答得到修正 |
| 后续上下文变化 | 保存失败经验，下次检索使用 | 系统能跨尝试积累经验 |
| Agent 实现变化 | 修改文件检索工具、搜索策略 | 执行系统产生了可继承的变化 |
| 模型参数变化 | 用新经验继续训练模型 | 某些能力被写入参数 |
| 改进过程变化 | 改变实验选择、候选生成或训练方法 | 系统开始改进“如何改进” |

这些变化都可能有价值，但所支持的结论不同。保存一条笔记，不能直接证明系统已经能够自主研发下一代基础模型。

### 1.2 “递归”有强弱不同的含义

当前文献对 RSI 没有完全统一的操作性定义。有些工作将“持续修改 Agent 自身，让下一轮接着修改新版本”称为 RSI；更强的定义要求系统能自主改进研发过程，持续产生能力更强的后继系统。

我会把两件事分开看：

1. **改进是否能够接续。** 第一次改进得到的系统，成为下一次改进的起点。
2. **改进能力是否也在增强。** 新系统能否在相同资源下，更有效地发现下一次有用改进。

第一件事说明循环接上了；第二件事关系到循环是否越来越有力。即使第二件事在一段时间里成立，也仍然要讨论它能持续多久、能迁移到哪些任务。

这解释了为什么“有限范围内的 RSI 实验已经出现”与“完全自主、开放式 RSI 尚未得到证实”可以同时成立。下文提到某项工作时，会具体说明它把循环接到了哪里。

## 二、ReAct：让推理与行动交替推进

ReAct 来自 *ReAct: Synergizing Reasoning and Acting in Language Models*，论文于 2022 年发布、发表于 ICLR 2023。它把语言推理与环境交互交织起来：推理帮助安排动作，动作带回新观察，观察再影响后续决策。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

### 2.1 一个循环里发生了什么

经典表示是：

```text
Thought → Action → Observation → 下一步决策
```

三个部分分别承担不同职责：

- **Thought：** 分解目标、解释已知信息、选择下一步。
- **Action：** 调用搜索、代码执行器或其他工具，查询或操作环境。
- **Observation：** 接收工具实际返回的信息，更新任务状态。

Observation 需要来自实际环境。模型写出“测试通过了”，与执行器返回测试通过，是两种不同的证据。

下面是本文虚构的简化示例，用来说明控制流程：

```text
任务：修复订单列表翻页时遗漏部分记录的问题。

决策：先确认分页查询的排序规则。
行动：读取查询实现。
观察：查询只按 created_at 升序排列。

决策：时间相同的记录缺少稳定次序，需要检查分页条件。
行动：读取分页参数与相关查询。
观察：游标只记录 created_at，下一页要求 created_at 大于游标时间。

决策：时间相同的记录被跳过了，让排序与游标共同包含唯一 ID。
行动：修改实现并执行对应验证。
观察：根据实际运行结果，决定继续调整或结束任务。
```

Agent 能根据新证据改变路线，不必在开始时就知道全部答案。

### 2.2 状态在变化，执行策略未必在学习

设 $h_t$ 是当前任务的历史，包括目标、动作与观察，$a_t$ 是下一步动作。可以简化表示为：

$$
a_t \sim \pi_{\theta,P}(\cdot \mid h_t),
\qquad
h_{t+1} = \operatorname{Append}(h_t, a_t, o_{t+1})
$$

历史 $h_t$ 变化，Agent 会产生不同动作，但参数 $\theta$、提示词 $P$ 或工具实现未必改变。

**同一个策略在不同信息下做出不同决策，是对当前任务的适应；把经验保存为影响后续任务的变化，才进入持久改进的讨论。**

ReAct 本身不规定任务结束后必须删除历史，也不自动提供跨任务学习。它可以与训练、记忆和反思结合，这些能力由额外机制提供。

此外，ReAct 不要求每一步都向用户打印完整的 Thought。原论文讨论了不同任务中的推理频率。工程上更值得检查的是：工具调用、环境反馈和任务状态是否形成有效循环。[ReAct 的方法说明](https://arxiv.org/html/2210.03629v3)

### 2.3 一次纠错与长期进步之间还有距离

ReAct 适合信息逐步揭示、行动结果影响下一步的问题，例如查资料、排查故障与操作软件。它也可能误读工具结果、重复无效动作，或在过长上下文中丢失关键约束。

一个 Agent 可以擅长在本次任务中纠错，却在一百次任务里反复犯同一种错误。执行循环解决了“如何继续做”，但未必解决“以后怎样少走弯路”。

## 三、RSI：把执行系统也放进改进循环

把视角从一次任务移到多个版本，结构就发生了变化。

![ReAct 在单次任务中交替决策、行动与观察；外层改进循环根据执行证据生成和评价候选版本，让通过评价的变化进入后续运行。](/images/posts/react-rsi/01-two-loops.svg)

*图 1：两种循环可以嵌套。外层流程是本文的概念模型；更强的递归还需要验证改进者本身是否随之增强。*

### 3.1 改进循环至少要说明六件事

| 环节 | 具体问题 | 缺失后的结果 |
| --- | --- | --- |
| 获取经验 | 当前版本在哪些任务上遇到什么问题？ | 改动缺少针对性 |
| 提出变化 | 准备改哪部分，预计改善什么？ | 难以判断改动原因 |
| 实现候选 | 能否得到可独立运行的新版本？ | 只有建议，没有系统变化 |
| 评价候选 | 在什么标准与预算下，新版本更好？ | 把自我肯定当成进步 |
| 选择与保存 | 哪些变化进入后续运行？ | 经验无法形成积累 |
| 接续改进 | 新版本如何参与下一轮？ | 只完成一次离线优化 |

“自己评价自己”并非 RSI 的必要条件。反馈可以来自执行结果、形式化验证、保留数据、用户结果或人工判断。自主提出改进与可信地确认改进，是不同职责。

### 3.2 递归如何在形式上出现

用 $U_k$ 表示第 $k$ 轮的改进过程，$D_k$ 表示可用经验，$E$ 表示评价规则：

$$
\widetilde{A}_{k+1} = U_k(A_k, D_k)
$$

$$
A_{k+1} = \operatorname{Select}_{E}(A_k, \widetilde{A}_{k+1})
$$

先产生候选，再决定是否采用。候选不一定更好，所以 $A_{k+1}$ 也可能仍是旧版本。

若 $U_k$ 始终由外部固定程序提供，这描述的是持续改进 Agent 的过程。进一步，若改进者由当前系统构成，或者改进方法本身也进入可修改对象，可以写成：

$$
U_k = \operatorname{ImproveWith}(A_k)
$$

此时，新版本既影响任务执行，也可能影响下一轮候选的生成、实验安排或搜索效率。这是“递归”最值得关注的部分。

这些公式是机制示意，不是性能保证。它们描述谁调用谁、谁修改谁，没有证明每轮都会进步，更没有证明改进会加速。

### 3.3 更会写代码，不等于更会改进研究者

下面两条命题需要分别验证：

> 新 Agent 更擅长完成代码任务。

> 新 Agent 更擅长改进 Agent。

两者可能相关，但第二项还涉及诊断系统缺陷、提出研究假设、设计实验和识别假改进。普通编码任务的分数上升，只提供间接证据。

我认为，更有说服力的 RSI 实验应当把新版本重新放回“改进者”的位置，在相同预算下比较它能否更快、更稳定地找到有用改进。

## 四、拆开内部结构：它究竟怎样改进自己

RSI 没有一套通用、固定的架构。下面是我综合现有工作提出的参考设计，用来解释各部分如何配合。

![自我改进系统的参考结构：任务产生证据，改进器生成候选版本，候选在固定条件下执行；评价与版本档案决定后续采用的系统，独立任务用于检查泛化。](/images/posts/react-rsi/02-improvement-system.svg)

*图 2：运行候选和评价候选是不同步骤。参与反复筛选的数据，不能同时承担最终独立验证的职责。*

### 4.1 可修改对象：系统需要能够“看见”自己

Agent 要修改工具或控制流程，就需要读取相应代码、配置与运行记录。仅仅告诉它“请变得更聪明”，没有给出可改变的对象，最终容易只得到一份建议。

可修改对象决定搜索空间。只开放提示词，它能寻找提示词变化；开放工具实现，可以探索检索与编辑方式；开放训练流水线，则可能提出数据、损失函数或优化算法的变化。

范围越大，候选越丰富，评价成本也越高。改两句提示词和训练一个新模型，都可以放进“提出—执行—评价”的框架，但所需资源相差很大。

### 4.2 经验记录：保存能够支持归因的信息

“任务失败了”不足以指导改进。需要知道失败发生在哪一步、当时看到了什么、执行了什么，以及结果由什么证据确认。

例如，Agent 没找到正确文件，可能因为搜索词不合适、工具截断了结果、忽略了返回内容，也可能因为代码库缺少目标实现。这几种情况要求不同修改。

我会同时保留任务结果和过程证据。模型生成的失败解释可以作为假设，后续实验再判断它是否解释了真正的问题。

### 4.3 候选生成：在不同方向之间分配尝试

模型可以根据失败记录提出局部改动，也可以结合历史版本寻找新的工作流。这里会遇到探索与利用的取舍：继续打磨当前最好的方案，还是尝试暂时较差、结构不同的方案？

前者容易获得短期收益，后者可能提供未来需要的中间步骤。因此，版本档案除了帮助回滚，还可以保存不同路线、失败原因和版本关系，支持后续搜索。

### 4.4 执行与评价：改得更好需要可比较的证据

每个候选都需要在明确条件下运行：使用什么模型、哪些任务、多少 token、多少执行时间，以及能够访问哪些信息。

我倾向于先固定预算，再比较任务结果。新版本如果把调用次数翻倍，也可能表现更好，但这无法直接说明资源使用效率提高了。

评价还需要覆盖真实目标。代码修改通过已有测试，是有用证据；测试的覆盖范围仍然限制结论。客服 Agent 减少回复轮数，也可能只是更早结束了尚未解决的问题。

### 4.5 选择与继承：改动必须进入后续运行

新版本需要被完整保存，并明确它依赖的模型、提示词、工具与记忆版本。只保存源码却丢失关键配置，就很难判断后续效果来自哪次改进。

继承可以表现为工具、工作流、提示词、记忆规则或权重的变化。系统也可以保留多个候选，让不同任务使用不同版本，不必始终只有一个全局赢家。

### 4.6 改进器本身：最深的一层递归

当系统开始修改“如何挑选实验”“如何生成候选”“如何分配预算”，它就在改变改进过程。

若评价方法也能改变，还要回答：分数上升来自能力增强，还是尺度变了？我会让评价器的改进通过另一个稳定参照验证，并保留新旧尺度的对照。评价器可以进步，同时需要证据说明它更接近真实目标。

## 五、几条代表路线分别做到了什么

这些研究经常一起出现在 RSI 讨论里，但它们处理的问题并不完全相同。

### 5.1 Gödel Machine：用证明决定是否重写自己

Schmidhuber 的 Gödel Machine 将自我改进形式化：系统包含描述目标、硬件与自身程序的公理，以及寻找有用自修改证明的过程；在证明修改有益后执行重写，证明搜索器本身也可以被修改。

其理论保证依赖公理、效用与可证明性。作者明确讨论了限制：真实有效的改进未必能被证明，有限资源下也未必能及时找到证明。[Gödel Machine 原作者说明](https://people.idsia.ch/~juergen/goedelmachine.html) · [理论限制](https://people.idsia.ch/~juergen/gmweb3/node19.html)

这条路线留下的问题至今有效：**系统凭什么相信修改自己会带来净收益？** 今天很多方法将回答从数学证明转向经验评价，同时也继承了经验评价的不确定性。

### 5.2 Self-Refine 与 Reflexion：让反馈影响下一次尝试

Self-Refine 让同一个模型生成答案、提供反馈、继续修改答案，主要发生在推理阶段。[Self-Refine](https://arxiv.org/abs/2303.17651)

Reflexion 将对任务反馈的语言反思存入情景记忆，使后续尝试能使用这些经验；其基本方法不通过更新模型权重实现学习。[Reflexion](https://arxiv.org/abs/2303.11366)

它们提供了反馈、反思和经验复用等重要组件。具体实现可以限定记忆只服务于一个任务，也可以扩展复用范围；仅凭“保存反思”还不能推出系统会改进自己的学习算法。

### 5.3 STOP：把改进程序作为程序的改进对象

STOP（Self-Taught Optimizer）研究了一个更直接的结构：让调用语言模型的代码改进器，也成为被改进的代码。它将优化程序的能力反过来用于优化自身。

作者明确指出，实验中的语言模型本身没有改变，因此不将结果视为完整的递归自我改进。[STOP 原论文](https://arxiv.org/abs/2310.02304)

它的启发在于，自我改进可以先发生在可读写的软件层。模型参数冻结，也不妨碍围绕模型运行的程序变得更有效。

### 5.4 Darwin Gödel Machine：让不同版本成为后续探索的起点

Darwin Gödel Machine（DGM）让 Coding Agent 修改自身代码，用编码任务评价候选，并维护历史版本档案。它允许从不同分支继续探索，让暂时不是最优的版本成为后续改进的起点。

论文报告，在 SWE-bench Verified 的 200 题评估子集上，表现从 20.0% 提升到 50.0%；在完整 Polyglot 基准上，从 14.2% 提升到 30.7%。基础模型保持冻结，改进发生在工具、上下文管理与工作流等 Agent 设计上。这些分数对应论文的模型、预算与评估设置。[DGM 原论文](https://arxiv.org/abs/2505.22954)

需要保留两个边界：档案维护与父版本选择过程仍然固定；编码能力提升会改善自修改能力，是方法依赖的假设，不能直接当作已经充分验证的普遍结论。[DGM 方法部分](https://arxiv.org/html/2505.22954v3)

### 5.5 AlphaEvolve：可执行反馈支持算法搜索

AlphaEvolve 将语言模型生成程序、自动评价和进化搜索结合，应用于算法发现以及计算基础设施优化。Google DeepMind 报告了其对数据中心、芯片设计和模型训练相关流程的优化。[AlphaEvolve 官方介绍](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

它演化的对象通常是目标程序，不能一概写成“Agent 在修改自己”。我认为它对 RSI 的重要性，是展示了一条反馈路径：AI 发现的改进可以进入生产 AI 的基础设施。整个研发系统自主、连续地产生后继系统，还需要把更多环节接起来。

### 5.6 AIDE²：直接评价 Agent 的研究效率

2026 年 9 月的 AIDE² 在 Agent 控制代码层面进行双层优化：内层在固定预算下解决研发任务，外层修改内层 Agent，并根据隐藏数据上的结果选择版本。一次八天运行得到七次被接受的改进，收益还在四个未参与筛选的基准上接受了检查。[AIDE² 论文](https://arxiv.org/abs/2609.26457)

其递归范围需要准确理解：主实验的外层改进者固定为人工研发的 Agent，各轮接受的内层版本成为后续修改对象；论文另做了将发现的 Agent 放到外层的“ignition test”。作者认为，该实验尚不能确定新 Agent 比原改进者更有效率。[AIDE² 方法与实验](https://arxiv.org/html/2609.26457v1)

它给出了多轮、可迁移改进的证据，也把“更会做研究”与“更会改进研究者”之间尚未跨越的距离摆了出来。

## 六、网上流行的几种解释，应该怎样理解

### 6.1 “AI 改进 AI，必然引发智能爆炸”

这条推理通常是：更强的 AI 提高研发效率，更高的研发效率产生更强的 AI，于是形成不断增强的反馈。

反馈路径存在，不意味着增长一定加速。它取决于每个环节放大多少，以及研究难度、算力和实验周期如何变化。

2026 年 9 月的 *The Economics of Recursive Self-Improvement* 用反馈环中各环节的弹性分析加速条件，并区分对 AI 研发有效的狭窄能力与更广泛的经济能力。作者的粗略校准认为，当前反馈尚不足以形成自我维持的加速，但反馈在增强；这是依赖模型与参数估计的结论。[RSI 的经济学分析](https://arxiv.org/abs/2609.15802)

我会把“智能爆炸”视为需要满足一组条件的情景。它不能由一个不断运行的循环，或者几轮分数上升直接推出。

### 6.2 “测试时多想一点，就能通向无限改进”

增加推理时间、采样次数与搜索分支，可能提高某次任务找到好答案的机会。能否把搜索结果压缩成可复用的方法，是另一个问题。

假设两个系统达到相同正确率：一个每次都重新搜索一百条路径，另一个从经验中学会优先尝试哪几条路径。它们的单次结果相同，长期成本却不同。

我更关心的是：**一次昂贵探索之后，下一次是否更便宜、更稳定，或者能解决原先解决不了的问题。** 更大的推理预算，还不足以回答这个问题。

### 6.3 “自博弈与合成数据，可以摆脱人类数据的限制”

自博弈让系统参与生成任务，再通过解决任务学习。Absolute Zero Reasoner 让模型提出和解决代码推理任务，由代码执行器验证任务与答案，探索训练课程和推理能力的共同改进。[Absolute Zero](https://arxiv.org/abs/2505.03335)

这里的“零数据”需要放回实验设置理解：它针对该训练过程不依赖外部任务数据，并不表示基础模型没有预训练，也不表示系统不依赖人类设计的执行环境。

我认为关键在反馈来源。程序能否运行、证明是否有效、实验结果是否可重复，都给生成内容增加了约束。若任务与答案只在模型的文字判断中互相认可，循环可能越来越自洽，却越来越偏离真实问题。

模型崩塌研究展示了无差别使用递归生成数据可能造成分布信息丢失的风险。它不意味着所有合成数据训练必然失败，而是提醒我们检查真实数据、验证机制与数据分布如何被保留。[模型崩塌研究](https://www.nature.com/articles/s41586-024-07566-y)

### 6.4 “能改写所有东西，才算真正自主”

修改范围、自主程度、改进效果是三个维度。系统即使能改动全部源码，也可能无法产生有效改进；只允许修改一个关键模块，也可能获得清晰、可持续的收益。

我更愿意把自主程度落实到具体环节：谁决定研究什么，谁提出候选，谁安排实验，谁判定成功，谁把结果用于下一轮。一个“全自动”的标签，无法代替这些问题。

## 七、ReAct 与 RSI，究竟差在哪里

| 比较维度 | ReAct | RSI |
| --- | --- | --- |
| 核心问题 | 当前任务下一步怎样行动？ | 系统及其改进过程怎样变得更有效？ |
| 主要循环 | 推理、行动、观察 | 经验、候选修改、评价、继承 |
| 典型时间范围 | 一次任务内的多个步骤 | 多次尝试、任务或系统版本 |
| 主要变化对象 | 当前任务历史与行动计划 | 提示词、记忆、工具、控制流程、参数或改进方法 |
| 反馈的作用 | 调整下一步行动 | 决定哪些变化进入后续系统 |
| 是否必然更新权重 | 不需要 | 也不需要，取决于研究范围 |
| 是否必然跨任务积累 | 本身不提供 | 需要说明保存、复用与适用范围 |
| 怎样证明有效 | 任务完成质量、步骤成本 | 版本收益、独立任务表现、改进成本与持续性 |
| 典型失败 | 误读观察、重复行动、偏离目标 | 评价过拟合、错误继承、搜索停滞、成本失控 |

RSI 系统可以使用 ReAct 来读取自身代码、执行实验和分析结果；ReAct Agent 也可以由外层自我改进过程持续更新。

所以，“从 ReAct 到 RSI”更适合表达观察视角的扩展：从任务执行扩展到系统演化。ReAct 仍然可以是其中的执行方式。

继续看前面的分页问题：修改业务仓库的分页代码，完成的是任务；发现自己总因读取不完整而误判，并改善自身文件读取工具，发生的是 Agent 改进；新版本进一步更有效地发现和验证此类改进，才为更强的递归提供证据。

## 八、现在走到了哪里，证据还缺什么

截至本文检索日期，我的判断是：**AI 已经能参与自己的研发，特定范围内的 Agent 改进循环也已有实验结果；持续自主地推动通用能力加速增长，仍然缺少充分证据。**

OpenAI 在 2026 年 9 月公开讨论研究加速，描述了受人类指导、完成明确研发任务的自动化能力；其同期说明仍将完全自主的递归自我改进视为尚未发生的状态。[研发加速报告](https://openai.com/index/research-acceleration-view-inside-openai/) · [对完全自主 RSI 的说明](https://openai.com/index/ai-policy-window/)

Anthropic 也报告了 AI 对内部研发的参与，同时表示尚未达到完全自主设计和开发后继系统的程度，且 RSI 并非必然发生。[When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)

这些是机构对自身进展的公开陈述，需要结合评估方法、公开实验与独立复现理解。

### 8.1 写出更多代码，不等于产生更多有效研究

代码量、实验数与工具调用次数容易统计。真正关心的通常是：新方法是否成立，能否迁移到更大规模，以及节省了多少资源。

一个失败假设也能产生大量代码与实验。把代码产出增长直接换算成研发效率增长，会遗漏问题选择、结果解释和大规模验证的成本。

AI4AI-Bench 尝试专门评价 Agent 修改训练算法的能力，避免数据收集或超参数调整掩盖算法设计问题。作者报告，在所评估配置中，许多提交没有真正改变模型如何学习。[AI4AI-Bench](https://arxiv.org/abs/2608.20318)

结果只适用于该基准与实验配置，不能推广成“AI 永远做不了算法研究”。它说明自动完成工程步骤与提出有效学习算法，需要分别测量。

### 8.2 隐藏数据也可能被反复筛选间接用掉

Agent 看不到一组题目，但每提交一个版本都能得到总分，这个分数就会影响后续搜索，因此这些题目已经参与了版本选择。

隐藏内容减少了直接利用答案的机会，却不能让反复使用的筛选集自动成为独立测试集。要判断泛化，仍需要未影响选择的新任务，必要时还要更换任务分布。

我很在意：**是在熟悉的评价器上越做越好，还是在下一批真实问题上也更好？**

### 8.3 最佳分数曲线会天然显得越来越好

如果每轮只保留最高分版本，“历史最好分数”按定义不会下降。仅展示这条曲线，容易让持续试验看上去像持续进步。

更有用的信息包括：每次接受改进消耗多少预算，重复运行后收益是否还在，独立任务表现怎样，改进失败的频率有多高。停滞区间也应当出现在我们的视野里。

### 8.4 错误也会被继承

自我改进让成功变化积累，同时也可能保留错误归因与偶然获胜的修改。一次幸运评价使坏版本成为后续起点，影响可能延续多轮。

对我而言，版本记录、实验可复现性与独立评价都是学习机制的一部分：它们决定系统在积累能力，还是在积累对评价器的误解。

## 九、我的判断：未来取决于哪些环节能接起来

### 9.1 更可能先成熟的是局部改进循环

我倾向于认为，近期更容易稳定应用的自我改进，会围绕边界明确、反馈便宜的对象展开，例如工具接口、检索方法、上下文组织、搜索策略与特定算法。

这些对象允许较快产生候选并比较效果，也容易把有用改动带入下一轮。基础模型架构、训练数据体系与开放式科研的周期更长，评价也更困难。

这是基于当前反馈条件的判断，不是给不同路线设定不可跨越的上限。

### 9.2 改进会把瓶颈推向下一环

用一个示意的时间模型理解这个问题：

$$
T_{\text{cycle}} = T_{\text{proposal}} + T_{\text{experiment}} + T_{\text{validation}}
$$

假设研究周期中，提出方案与编写代码占 20%，实验与验证占 80%。即便把前者压缩到几乎为零，整体也只从 100 缩短到 80，约为 1.25 倍加速。数字只是示例，却说明了某一环节的大幅提升，未必带来同等规模的整体提升。

如果实验也被优化，瓶颈可能继续移动到数据获取、硬件供应或确认方法在真实场景有效。递归系统能否持续增长，要看它能否不断改善这些新瓶颈。

### 9.3 可靠反馈会成为越来越重要的资产

候选方案更容易生成后，稀缺的可能转向判断方案的能力：可复现环境、可信结果、新任务、长期用户反馈，以及能区分偶然收益与稳定进步的实验设计。

我会用下面这个概念关系提醒自己观察整个链条：

```text
提出有价值的候选
        ↓
正确识别真正有效的变化
        ↓
将变化稳定地带入后续系统
        ↓
在新任务上仍然获益
        ↓
用这些收益支持下一轮改进
```

任何一环持续失效，都可能让循环停滞。让 Agent 更敢修改自己，只增强了其中一部分。

### 9.4 同时观察“做事能力”和“改进能力”

我会同时记录两类结果。第一类是任务能力：正确率、完成质量、延迟与成本。第二类是改进能力：发现一个经独立验证的改进需要多少资源，这些改进能连续出现多少轮。

如果任务能力提高，但每次改进越来越昂贵，系统可能只是在逐步用尽一片容易搜索的空间。如果固定预算下能持续找到新改进，且新 Agent 更有效地推动后续改进，才更接近递归加速的证据。

### 9.5 人的职责会随自动化范围改变

更多实现与实验步骤交给 Agent 后，人可能需要花更多精力定义值得解决的问题、识别评价盲区，并判断实验结论能否支持实际采用。

这不要求人逐行理解每个候选，但要求在关键决定上仍能说明：目标是什么，证据支持到哪里，哪种结果会让我们改变判断。

我期待 RSI 首先改变软件的改进方式。一个系统除了交付功能，还能把使用过程中的证据转化为下一版的改进提案；这些提案经过比较，逐渐减少重复错误和无效尝试。

更远的未来是否会出现持续加速的自主研发，取决于改进能否跨越任务、版本、模型与实验规模不断延续。今天的工作已让这个问题可以被部分实验化，但还没有给出完整答案。

回到最初的 Agent：这次把问题解决了，很重要；下一次能够少走弯路，也很重要。我更想追问的是，**它留下了什么可靠的改变，以及这些改变是否让下一次改进本身也更容易。**
